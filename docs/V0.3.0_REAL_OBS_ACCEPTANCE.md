# v0.3.0 真实 OBS + 本地 RTMP 验收手册

> 当前为独立开发分支 `feat/v0.3.0-one-click-live`，不得将模拟 OBS/WebSocket 检查当作真实推流验收。

## 三层验收证据

| 级别 | 验证范围 | 判定方式 |
|---|---|---|
| 1. 自动化业务模拟 | Electron IPC、商品列表、AI 回复/语音优先级、开播/停播、失败回滚 | Windows/macOS CI，允许模拟 OBS |
| 2. 浏览器真实播放 | OBS 输出页面在真实 Chromium 解码图片/视频、播放 WAV 并回执 | Browser Source 本机服务 CI |
| 3. **真实直播音视频** | **真实 OBS.app / OBS Studio → 本机 RTMP 接收端 → FFprobe/FFmpeg** | **必须录制到视频轨+非静音音频轨，且画面存在真实变化** |

只有级别 3 验证通过，才能宣称“本机真实 OBS 推流闭环通过”；这仍不代表已获抖音正式开播许可。

### Windows 120 秒实测数据

- 真实录制文件：`recordings/actual-obs.flv`；录制总时长 **123.999 秒**。
- 视频：H.264，1280×720；每秒抽取 **124 帧**，其中 96 帧红色主导、28 帧蓝色主导；不是全黑或静态不变。
- 音频：AAC，48 kHz；音频峰值 **12,870**；RMS 约 **1,411**（用 FFmpeg 独立解码复算）。
- 从最终 RTMP 解码音频中再次识别测试时注入的 **440 Hz** 音调（幅值约 **11,998**；620 Hz 参考幅值约 22），不只是验证有音轨。
- OBS 本地独立预览和正式开播均有真实就绪回执；连续输出 120 秒未记录重新连接；停播后复查 OBS 场景列表只含 `Base`，没有残留 `AI Live Commerce - ...` 场景。
- 曾经发现 120 秒输出结束后的临时场景清理未确认；新增有界验证与重试，**上述最新完整流水线已经重新通过**。
- 证据产物可在 [真实 Windows 验收运行记录](https://github.com/dylanlucus26/ai-live-commerce/actions/runs/39732359045) 里的 `windows-official-obs-local-rtmp-evidence` 下载。

**重要边界：** 上面的 440 Hz 是程序合成的 PCM/WAV 测试音，不是调用真实 MiMo API 得到的带货讲解。它充分证明音频通过 OBS Browser Source 进入真实 RTMP；不能代替真实 TTS 音色、商品文案、弹幕打断恢复和平台接收验收。

### Mac 阻塞原因与下一步

GitHub 托管的 macOS 14 和 macOS 15 ARM64 图形环境都缺少 OBS 需要的用户授予权限，OBS 应用进程存在但初始化不能走到 WebSocket 服务阶段；脚本现已做到 45 秒有界失败并保存内部日志。**这不构成 Mac 产品不支持 OBS 的证据，更不是 Mac 通过验收的证据。**

Mac 完整实测需要一台具备实际图形登录会话、允许正常安装官方 OBS 并通过 macOS 权限对话框的**远程 ARM64 Mac 测试机**（可独立于用户的 MacBook）。当前连接的 GitHub 托管 Runner 未能提供这个条件；不可通过伪造权限或跳过 RTMP 媒体验证来宣布完成。

## 2026-10-24 断流恢复及重新开播验收（最新证据）

**Windows 已通过完整故障恢复复测**：[GitHub Actions #40073098571](https://github.com/dylanlucus26/ai-live-commerce/actions/runs/40073098571)，代码提交 `882199a6`。

1. **正常推流**：OBS 32.2.2 + WebSocket 5.7.4，连续 120 秒；RTMP 录制 124.132 秒，H.264 + AAC，非黑屏且含注入的 440 Hz WAV。
2. **原生安装版界面**：使用真实 Electron 点击「本地演练」时未推流；点击「开始直播」后，真实 RTMP 文件录制 17.332 秒（H.264 + AAC，合成 TTS 测试音）；点击「结束直播」后清理 OBS 场景。
3. **接收端故障注入**：仅杀死 CI 自己创建的本机 FFmpeg RTMP 接收进程。OBS 仍报告 `outputActive=true`、`outputReconnecting=false`，因此单靠 OBS 指标不能发现实际收流中断；**通过独立本机接收端探测**，应用在约 1 秒内将流状态转为 `failed`，但保留归属本次账号的安全停播能力。
4. **恢复**：本账号安全 StopStream，原始 `Base` 场景恢复、无临时场景遗留；恢复本机接收端后不重启 OBS 或控制器直接再次开播，并由 **FFprobe 验证第二段独立 RTMP H.264 录制持续 4.365 秒**；再次停播后原场景仍完整。
5. **常规回归**：[双平台 CI #40073098515](https://github.com/dylanlucus26/ai-live-commerce/actions/runs/40073098515) 两个任务均成功；包括单元测试、打包的 Windows/macOS Electron 业务回归（业务中 OBS/付费平台部分仍模拟）。

### 2026-10-24 恢复后音轨独立复测

在 [Windows 官方 OBS 完整复验 #40073690964](https://github.com/dylanlucus26/ai-live-commerce/actions/runs/40073690964) （代码 `80929e57`）中，增加了故障恢复后的**第二段音频**验证：

- 先完成 120 秒正常流（实际 FLV 124.099 秒）以及已打包 Electron 界面的「本地演练 / 开始直播 / 结束直播」测试；音视频均录制成功。
- 关闭测试自己拥有的本地 RTMP 接收进程，OBS 在故障时仍报告 active 且 reconnecting=false，软件靠独立本机监听状态探测约 1 秒识别接收端缺失。
- 安全 StopStream 和清理场景后，无须重启 OBS，恢复本地接收端并再次开播；Browser Source 再次播放 440 Hz WAV。
- 第二段独立 FLV **6.632 秒**，FFprobe 验得 **H.264 视频与 AAC 音轨**，FFmpeg 解码音频峰值 **11,641**，且检测到注入的 440 Hz 音调。
- 再次正常停止后，场景列表仍与原始集合一致，无软件临时场景泄漏。

这完成了 **Windows 本机 RTMP 断流后的二次开播音画恢复**，但真实 MiMo 服务、抖音房间实际收流、macOS ARM64 官方 OBS 和 2–8 小时稳定性**仍未通过验收**。

**限制：** 本机 RTMP 监听探测仅适用于 `127.0.0.1`、`localhost` 或 `::1` 的明确配置，证明监听端口可连接，不能证明远程平台或观众真正收到音视频；远程抖音必须有平台侧确认。Windows 真实测试使用合成 WAV，不代表真实 MiMo API、实际抖音授权和直播规则已验收。

## 2026-10-24 OBS 进程崩溃故障注入（真实 CI）

**通过**：[Windows 官方 OBS 完整运行 #40074340902](https://github.com/dylanlucus26/ai-live-commerce/actions/runs/40074340902)，代码提交 `73fa844f`。

在保留前述全部正常开播和本地 RTMP 接收端丢失恢复测试的基础上，又用 CI 自己启动的真实 OBS 32.2.2 进程执行了以下严格故障测试：

1. OBS 实际推流中，仅终止当前 CI 自有的 OBS 进程；WebSocket 确实失联，软件控制器从 `streaming` 转为 `failed`，没有错误宣称仍在正常直播。
2. OBS 不可达时不能假装「结束直播已成功」，已确认的流归属保留，用于后续安全清理；不接管、停止其他人的流。
3. 重新启动 OBS，确认 WebSocket 和输出状态恢复；释放旧会话及预览，原场景恢复、无软件临时场景。
4. 使用同一测试环境重新启动 RTMP 接收端，再次开播并停播；**新生成的 FLV 为 4.632 秒可解码 H.264 视频**，而不是只通过 API 状态。

**重要区别：** 这次重启后的最后一段仅核验恢复视频轨。上一轮 [#40073690964](https://github.com/dylanlucus26/ai-live-commerce/actions/runs/40073690964) 已对「RTMP 接收端崩溃后重新开播」核验恢复后的 **H.264 视频和 AAC 测试声音**。两种故障不能互相替代，也都不能证明真实 MiMo API 或远程直播平台收流可用。

## 2026-10-28 Mac ARM64 官方 OBS 真实 CI 验收：原生推流通过，产品 Browser Source 仍失败

使用官方 OBS Studio 32.2.2 / obs-websocket 5.7.4，在 GitHub 托管 macOS 15.7.9、macOS 26.6.2 两套 ARM64 Runner 完成独立实测。

[真实 macOS 15 / 26 完整测试与诊断 #40656710803](https://github.com/dylanlucus26/ai-live-commerce/actions/runs/40656710803)。工作流有意保持失败，因为产品的 Browser Source 首帧门槛未通过。

- 官方 OBS 通过 **原生 Cocoa** 模式成功启动，真实 WebSocket 4455 可连接。旧的 Qt offscreen 模式在两套 Mac Runner 上发生 SIGSEGV 11，已弃用。
- 软件通过真实 OBS API 创建专用场景、浏览器源、设置本机素材 URL 并切换场景。GetSourceActive 返回 videoActive=true、videoShowing=true，URL 参数正确。
- **产品路径仍失败**：等待约 40 秒，商品 HTTP 服务统计 index=0、playlist=0、media=0、ready=0；即 OBS CEF 未真正请求图片或视频页面。OBS 真实截图调用及浏览器源刷新都未改善，因此不允许把页面标记为视觉就绪。
- **原生 OBS 对照组通过**：用官方 OBS 的原生 ffmpeg_source（不是软件的 CEF 源）进行本机 RTMP 推流，macOS 15 和 macOS 26 均产生 **10.165 秒 H.264 视频 + AAC 非静音音频**。FFmpeg 解码峰值分别为 **4,833** / **4,836**。证明 OBS 的 Mac 编码、音频混音和 RTMP 传输有效，但不能代替产品实际商品轮播和 WAV 注入验证。
- macOS Electron 构建、启动、原生 IPC 和模拟业务测试独立通过，但真实 Browser Source 仍无实际 RTMP 音视频证据。

**当前判定**：Mac 原生 OBS→RTMP 传输层已验证；AI Live Commerce v0.3.0 Mac 一键直播端到端 **尚未验收通过**。下一门槛是具备正常可交互图形桌面、权限授权的 ARM64 Mac 上实测 CEF 第一帧、商品视频轮播、WAV 音频进入 RTMP 和停播资源清理。不得将独立原生媒体源控制组的通过误标为产品验收通过。

## 真实通过标准

1. OBS 版本及 WebSocket v5 响应可信，开播前 OBS 未占用外部直播。
2. 测试服务仅监听 `127.0.0.1:1935`，地址为 `rtmp://127.0.0.1:1935/live`，密钥是临时测试值。
3. 创建本次专用 OBS 场景，能看到商品 PNG 和 MP4 视频循环；不破坏其他 OBS 场景。
4. Browser Source 回报画面准备就绪，点击直播流程后 OBS 状态由 idle 进入输出。
5. 经 Browser Source 播放 WAV，收到完整播放回执。
6. 接收端实际生成 FLV 文件，使用 FFprobe 检查视频轨、音频轨、解码帧和有效流时长。
7. 使用 FFmpeg 解码音频样本，排除静音；逐秒抽取实际视频帧，排除黑屏与画面始终不变。
8. 停播后 `outputActive=false`，临时场景删除，原场景和原流服务配置恢复。
9. 已经存在外部 OBS 推流时必须拒绝接管/改写推流服务；请求确认丢失也不能误停止别人的流。

**未通过任何一项，不得将真实音视频推流验收标记为通过。**

## 长时间运行

测试脚本支持 `AI_LIVE_OBS_SOAK_SECONDS`，范围为 11–14400 秒（最长 4 小时），每 5 秒核对一次 OBS 是否仍处于稳定推流且未进入 reconnecting 状态。

Windows 已完成 120 秒真实测试，但**没有**完成 2 小时/8 小时以上的长时稳定性与故障恢复测试。Mac 仍待具有完整 GUI/TCC 授权的 ARM64 测试机；后续再执行完整长时监测。

本地测试时，必须先启动**已经得到用户授权的真实 OBS Studio**、本机 RTMP 接收端，并确保 OBS WebSocket 已开启。脚本会短暂切换 OBS 的推流服务到本机地址，**启动前检查 OBS 未处于推流状态**，结束后尝试恢复原推流服务，测试期间不要手动切换原有配置。
